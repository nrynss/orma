**Why no fix works without a schema change.** Findings 1 and 2 share a root: nothing records who moved the run at the moment of the guarded write. Two ways to record it exist today, and neither works:

- **On the run itself.** `call_runs` has no free column for an event id. Every jsonb column belongs to another task's contract. Two webhook events for one call write identical values, so no existing value can tell them apart.
- **In a separate write.** A row on `webhook_events` or `call_events` is a second REST request. PostgREST gives no transaction across two requests, and no trigger or RPC can bridge them without a migration.

The separate write fails in a real ordering, not just in theory:
- The webhook's update lands, then its invocation is killed before the record is written. The 5-minute lease reclaim (`REFRESH_LEASE_MS`) retries it as a redelivery, which finds a terminal run and no record.
- A poll whose update landed but whose `polled` insert failed leaves exactly the same picture.

The redelivery cannot tell these two cases apart, so `applied` and `already_resolved` would each be false in one of them.

**Proposed design, in the contract change row.**
- **Column:** add a nullable `call_runs.terminal_writer text`. Every guarded pending-to-terminal update sets it in the same UPDATE as `state`, so the record is atomic.
- **Values:** the webhook writes `webhook:&lt;event_id&gt;`. The poll writes `poll` on its terminal, give-up and missing-call-id writes.
- **Receiver:** when the update matches no rows, it reads the column. It records `applied` only when the value matches its own tag exactly, and `already_resolved` otherwise, including null. `earlierAttemptApplied` and the `redelivered` flag go away.

**Why that design holds in every ordering.** The writer's tag and the state land in one statement, so they can't disagree.
- A killed invocation or a failed timeline insert leaves the tag correct.
- A second event for the same call finds the first event's full id, so it cannot claim the write (finding 1).
- A poll that won names itself on the run, whatever happened to its `polled` row (finding 2).
- Dispatch's own terminal writes never pass the pending guard. They leave the column null, which correctly reads as "someone else".
