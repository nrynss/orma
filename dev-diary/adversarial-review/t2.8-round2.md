## Claims I judged, with the measurement behind each

**The recorded body equals the live body byte for byte. Verified.** Both halves
ran on run `...0005` with the same briefing and the same idempotency key. The
live half posted the body to the stubbed CALL-E host, and the dry half stored
its copy. The stored copy came back out of `call_events` and compared equal.

```text
live body sha256   d46d2bffa2ced26104ac931201d83fa191b8d21d4a78b6ddfe16f2669976d911 (4553 chars)
stored body sha256 d46d2bffa2ced26104ac931201d83fa191b8d21d4a78b6ddfe16f2669976d911 (4553 chars)
```

The live half wrote no body to the timeline at all, so the dry copy is the only
persisted one. That is what makes finding F1 an exposure.

**The embedded fixtures match the committed recordings. Verified.** Both
constants equal `JSON.parse` of the committed files under `testdata/calle/`,
compared as `JSON.stringify`, so key order counts. Pin `m4` above shows the
comparison fails when either side drifts.

**The fixture choice for a failed and an invalid result. Verified, with a
residual risk.** The failed fixture lands an invalid result, not a failed one.
`results.valid` reads false, `results.error` reads `structured_result must be an
object`, the transcript holds zero turns, the run reads `failed` with
disposition `not_answered`, and `completed_at` still comes from ingestion. The
failed fixture carries a null structured result, which is what makes the invalid
branch reachable without a call.

**A claim response cannot lose `dry_run` between the RPC and the dispatcher.
Verified. The field is the only guard for the per-run flag.** The RPC returns
the whole `call_runs` row. A dispatch call handed a run object with no `dry_run`
field under `ORMA_DRY_RUN=false` placed a real call, while the database row
carried `dry_run` true. The field must stay mandatory and the RPC must keep
returning it.

**No path reaches CALL-E with the setting unset. Verified.** Only `calle.ts`
issues `POST /v1/calls`. The poll and the webhook issue `GET /v1/calls/{id}`,
and both select runs in `dispatched` or `awaiting_result`. Every dry run I
produced ended `completed` or `canceled`, and no marker run in either pending
state carried a `fixture:` call id. That count came back zero. A dry run whose
ingestion fails leaves a terminal run with a null `completed_at`, which T2.7a's
finaliser will select and re-fetch by `fixture:call_...`. That is a `GET` with a
synthetic id rather than a dial, and the finaliser does not exist yet.

**The 409 handling. Correct.** One `POST`, never retried, and never retried with
a different key. The run ends `failed` with `calle_failure`
`idempotency_conflict` and a `completed_at`, so it stays out of the finaliser
queue. `disposition` stays null, where the poll's failure path writes
`not_answered`. Nothing reads that column yet.

**The consent and confirmed-number refusal. Correct, and shared with the live
path.** Both run before the dry decision, so a rehearsal exercises the same
gates. A profile with no confirmed number produced `dispatch_refused` with
`profile has no confirmed E.164 number`. A revoked consent produced
`dispatch_refused` with `profile has no live outbound_calls consent`. Both
placed zero CALL-E requests, both left the run `canceled`, and both wrote no
transcript and no result. The refusal writes `completed_at` itself, which is
right, because a refused run has no provider payload for ingestion to timestamp.

**The timeline ordering when ingestion throws. Honest, and the run is left
recoverable in principle.** The dry dispatch records the terminal row and the
`dispatched` row, then the ingest call fails, so the timeline holds `dispatched`
alone with no `ingested` and no `finalised`. That is not a false claim, because
the run is terminal in `call_runs`. The run holds `{"state":"completed",
"completed_at":null,"calle_call_id":"fixture:call_tQA8nz1WGj9vfO30PxTosA"}`,
which is the finaliser's queue shape, exactly as the poll and the webhook leave
it. The only asymmetry is the synthetic id, which no CALL-E re-fetch can serve.

**The timeline when the terminal write fails. Nothing is written.** The
`claimed` row comes from `tick`, not from `dispatchClaimedRun`, so a direct
dispatcher call writes no `claimed` row. That is why the direct-dispatch
timelines above start at `dispatched`. A reviewer who drives the dispatcher
directly and expects a `claimed` row will not find one.

## Residual risk

**Nothing sets `call_runs.dry_run` in production.** The schema defaults it
false, the seed sets one row, and no other writer exists. The per-run override
is real and honoured, and it currently needs an operator `UPDATE`. T2.9 or P6
may own the surface.

**A run dispatched dry under the global default reads `dry_run` false.**
`call_runs.dry_run` is the operator override, not a record of what happened. The
only record that a run was dispatched dry is
`call_events.detail.dispatch_mode`. A consumer that reads the column to answer
"did this run really call?" answers wrong for a run the default protected. The
contract change records the same reading, so I am not raising it as a finding. It
is worth a column comment, because the spec sentence reads as if the column
reports the mode.

**T2.7a must not re-fetch a `fixture:` call id.** A dry run whose ingestion fails
is terminal with a null `completed_at`, so the finaliser selects it. The id is
synthetic, so the re-fetch cannot succeed, and the run would stay queued for
every later tick.

**A stranded `claimed` run can only be repaired with SQL today.** See finding
F3. The repair must fail such runs rather than re-queue them.
