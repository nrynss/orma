## The choice I made on N4, and why

The finding offered two repairs. I made the documentation true rather than
widen the count, for one reason that decides it.

A wider count has to include a run the recovery failed. That run dialled nobody.
A tick over it would then report `claimed: 1`, which is the shape round 2's F2
finding closed: a count that reads healthy over a dispatch that never happened.
The narrower reading cannot do that, because only a dispatch whose writes all
returned is counted. So the count stays as round 2 defined it and the sentence
above it stops overstating the measurement.

The one visible cost is that a failed dispatch reads `claimed: 0` even when the
call was placed. The run's state answers that, and the log line names the error.

## When the recovery writes themselves fail

The recovery's read or write can fail, and then the run keeps the state it had
and the log line names it. When the attempt had placed a call, the log also names
the accepted call id, because that id is the only surviving handle on the call:

```text
dispatch recovery failed for run <id> <message> accepted call <id> needs manual reconciliation
```

Nothing re-queues the run. A second dispatch could dial a person who was already
called, and that is the worse of the two failures, so the strand is left for a
human to repair rather than for a scheduler to redial. This is the one residue
the two M findings leave, and it needs the write path itself to be down, not just
one write. `S4(c)` in the round 3 review measured the same behaviour before this
round and the row still reads `claimed`.
