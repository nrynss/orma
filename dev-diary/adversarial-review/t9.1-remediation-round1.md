## F1: the live dot has its fill back

`background: var(--brand)` sits on the `.o-live-dot` rule, so the marker reads as a solid disc
rather than a transparent box inside a halo. The halo is untouched: `box-shadow: 0 0 0 4px
var(--brand-soft)` stays on the rule, and the `o-live-pulse` keyframes still breathe it from 2
pixels to 6 pixels.

The dot marks a call in progress, so it needs 3 to 1 against what it sits on. Measured against
the pane surface, `--brand` on `--canvas` reads 8.01 to 1 in light and 9.70 to 1 in dark. Round 1
predicted exactly those two numbers for a `--brand` fill, and the fix lands on them.

Round 1 read the before at 1.04 and 1.21 from a pixel sample. My rebuild of the pre-fix rule
reads the bare surface straight through the transparent box, which is 1.00 in both themes. The
two readings differ only in which part of the halo the sample caught, and both sit far below the
3 to 1 floor.

## F2: one declaration, at the intended period

The rule now declares `animation` once, as `o-live-pulse 1400ms ease-out infinite alternate`.
The second declaration, which repeated it at `var(--motion-slow)` and so resolved to 240ms, is
deleted. `--motion-slow` no longer means a pulse period in one file and a transition duration in
the gallery motion row. The pulse keeps a literal period, and the comment above it says so.

The accessibility guidance the finding names is met twice over. A full breath runs 2.8 seconds
at 1.4 seconds an iteration with `alternate`, which is 0.36 breaths a second against 2.08 before.
The flash threshold of three a second sits far above that. The `prefers-reduced-motion`
block in `tokens.css` also stops the pulse outright: with reduce emulated, `animation-duration`
computes to `1e-05s` and `animation-iteration-count` to `1`, in both themes.

## F3: the border box reaches the whole system

The base layer now resets `box-sizing: border-box` on `*`, `*::before` and `*::after`. This
restores the behaviour the retired sheet gave through `.o-app *`, and it now covers public pages
as well as the app shell. The reset sits under the base layer comment, after the light and dark
theme blocks and before the `html` rule.

Field's controls keep `width: 100%` with their padding and their border, and they now fit. The
control reads the same width as its field at every width I measured, namely 594 pixels against
594 at 1280, 326 against 326 at 360 and 286 against 286 at 320. Before the reset the input and
the textarea each overhung their field by 26 pixels, and the input's right edge landed 25 pixels
past the pane padding edge at every width.

The overhang also pushed the document wider than the viewport. At 320 in a single pane column
`scrollWidth` read 329 against `clientWidth` 320. It now reads 320 against 320. At 360 it goes
from 369 against 360 to 360 against 360, and at 1280 from 1289 against 1280 to 1280 against 1280.

One side effect is deliberate, and I record it so the re-reviewer is not surprised. `.o-switch-track`
declares 46 by 28 with 3 pixels of padding, so under the reset the track measures 46 by 28 rather
than 52 by 34. That is the size the stylesheet always declared. The thumb stays inside the track
on both sides, and the switch, the button and the field control all still measure 44 pixels tall.

## F4: the invalid border wins

The invalid rule repeats the control selectors and adds the `aria-invalid` attribute to each one,
so it outranks the plain control rule on specificity. It keeps its place at the end of the file.

A toggle on one element, in the live browser, proves the state wiring rather than two separate
elements. Set `aria-invalid="true"` and the input's computed `border-color` becomes `rgb(179, 38, 30)`
in light, which is `--danger` `#b3261e`, and `rgb(240, 144, 138)` in dark, which is `#f0908a`.
Remove the attribute and the border returns to `--border-strong`, `rgb(138, 132, 150)` light and
`rgb(111, 104, 128)` dark. Before the fix both reads returned the `--border-strong` pair, so no
invalid affordance reached the control at all.

## How I measured

I ran no dev server and no build, per the rules for this round. Each number above came from a
throwaway page under `/tmp`, built at measure time from the real `LiveDot.svelte`, `Field.svelte`,
`Switch.svelte`, `Button.svelte` and `tokens.css`. Nothing was added to the repository.

The page carries the CSS as Svelte 5.57 compiles it, so the scoping class, the renamed keyframes
and the `:global()` selectors are the real article rather than a paraphrase. I compiled the four
components one file at a time, which is a scoped check of this change and not the project gate,
and each one compiled with zero warnings. The markup then renders each control with the compiled
class, inside a pane that copies the gallery's own pane rule.

I loaded each page in headless Chromium at 1280, 360 and 320 wide, in both themes, and the phone
widths use one pane column as the gallery does. The before column comes from a second page built
from the same compiled CSS with the four remediation edits reversed, so the two runs differ only
by the fix. The pixel sample decodes a screenshot at a device scale of four and reads the exact
centre of the dot.
