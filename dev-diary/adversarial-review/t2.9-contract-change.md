# T2.9 contract change

T2.9 owns `supabase/functions/_shared/events.ts`,
`supabase/functions/materialise/index.ts` and, from the orchestrator's later
widening, `supabase/functions/_shared/calle.ts` and
`supabase/functions/_shared/finalise.ts`. It adds the `materialised` writer, the
rows that end a run a dispatcher cannot place, and the pins that go with both.
Six records belong here. One is a reading of the done condition, and the rest
name findings this task closed.

The change in the owned paths: `insertRuns` now asks for the representation and
returns the rows the database created. `materialise` then appends one
`materialised` row per inserted run, immediately after the insert succeeds, and
nothing when it fails. The return of the rows is what makes "one row per
inserted run" true rather than assumed, because a key already present is
ignored and comes back absent.

In `_shared/calle.ts`, the four paths that end a run before a call exists
append one `finalised` row that names the reason, and the poll-handover path
appends none.

## 1. The done condition reads delivery as T3.4's `deliveries` table

The block says a completed run reads "as an ordered story from materialisation
to delivery". The kind list ends at `finalised`, and no owner adds a kind.

**Reading.** Delivery of the receipt is T3.4's `deliveries` row and never a
`call_events` row. `_shared/deliver-telegram.ts` inserts into
`public.deliveries` (lines 214 to 221) and updates `sent_at` or `error` there.
It writes no `call_events` row. So a completed run's timeline ends at
`finalised`, and the delivery is read from `deliveries` by `call_run_id`.

The ordered read below shows the completed run ending at `finalised`. That is
the whole timeline, and the receipt is a second table rather than a ninth kind.

## 2. A failed or refused dispatch now ends with `finalised`

**Found by T2.9's first drive, and closed by the orchestrator's decision.** The
first drive showed a run whose dispatch CALL-E refused reading `claimed` and
nothing else, because `dispatchOne` and `recoverStrandedRun` wrote the failure
on the run and recorded no event. The timeline then stopped without a reason.

**Decision.** Close it with the existing `finalised` kind rather than a ninth
kind. `finalise.ts`'s `abandonRun` already ends a run without ingestion using
`state`, `outcome` and `failure_reason`, so a dispatcher that ends a run uses
the same shape. The kind list stays at eight. The orchestrator widened the
`owns` line to `_shared/calle.ts` for the four writers.

| Where | What | Pin | Mutation |
| --- | --- | --- | --- |
| `_shared/calle.ts` `refuseRun` | A refusal records `state: canceled`, `outcome: refused` and the reason, after the run write lands. | `missing consent is recorded and never reaches CALL-E`. Reverting the append fails it with `claimed` alone. | A refused run reads as a bare claim. The consent refusal, the unconfirmed number and the missing slot become invisible. |
| `_shared/calle.ts` `dispatchOne` 409 branch | The conflict records `state: failed`, `outcome: idempotency_conflict` and the reason. | `a CALL-E 409 is visible and does not retry with a fresh key`. Reverting the append fails it. | A reused idempotency key leaves no reason on the timeline, and that 409 is the one condition AGENTS.md calls a bug to fix. |
| `_shared/calle.ts` `dispatchOne` non-ok branch | The rejection records `state: failed`, `outcome: dispatch_failed` and the provider status. | `a rejected dispatch names the provider status on the timeline`. Reverting the append fails it. | A provider outage looks like a run that was claimed and abandoned. |
| `_shared/calle.ts` `recoverStrandedRun` | A stranded run the recovery fails records `state: failed`, `outcome: dispatch_failed` and the cause. | `a dispatch that throws before its terminal write leaves no run claimed`. Reverting the append fails it. | A run the recovery ends reads as a claim with no cause. |

**Ordering, so one move records one row.** Each path writes the run first, then
appends. The recovery reads the state before it writes, so a run the 409 or the
rejection already failed is not failed a second time, and the append happens
once. The 409 and rejection tests stub the run state, and the live drive
observed one `finalised` row per move.

**The poll-handover path records no `finalised` row.** A recovery that holds a
call id hands the run to the poll, because that story continues. Reverting any
of the four appends leaves that pin passing. The live drive reads `claimed`
alone at handover, then `polled, ingested, finalised` after the next tick.

**`terminal_writer` keeps the contract in the column comment.** A refusal and a
rejected or conflicted dispatch leave it null, which the comment already says.
The recovery keeps `dispatch_recovery`. No comment change is needed, and none
was made.

**Observed live, 2026-09-13, marker `t29`, against the shared stack.** The four
ordered reads, each one tick:

```text
refused   claimed | finalised {"state": "canceled", "outcome": "refused", "calle_call_id": null, "failure_reason": "call run has no source slot"}
conflict  claimed | finalised {"state": "failed", "outcome": "idempotency_conflict", "calle_call_id": null, "failure_reason": "CALL-E rejected this idempotency key with different inputs"}
rejected  claimed | finalised {"state": "failed", "outcome": "dispatch_failed", "calle_call_id": null, "failure_reason": "CALL-E dispatch returned HTTP 500"}
stranded  claimed | finalised {"state": "failed", "outcome": "dispatch_failed", "calle_call_id": null, "failure_reason": "CALL-E response missing id or status"}
handover  claimed
handover  claimed | polled | ingested | finalised {"state": "completed", "failure_reason": ""}
```

**Residual, revised in remediation round 2.** The append now retries inside
`recordCallEvent`, so a transient failure no longer loses the row. The append is
still not transactional with the run write, and a retry whose first request
landed can append a second row. See record 6.

## 3. The failure rows carry the same shape, and no new tag

`finalisedFailureDetail` in `_shared/calle.ts` builds `{calle_call_id: null,
state, outcome, failure_reason}`. Every row satisfies the helper's terminal
contract, and every state it writes matches `/(?:fail|error|cancel)/i`, so the
reason is required rather than optional.

**What the null `calle_call_id` means, corrected in remediation round 2.** It
means Orma stored no provider call id on this run, so the timeline has none to
name. That is a statement about Orma and not about CALL-E. A 409 disproves the
stronger reading, because CALL-E already held the idempotency key, so a call may
exist while Orma holds no id for it. `poll.ts`'s no-call-id row carries the same
meaning.

## 4. The insert now names the conflict arbiter

| Where | What | Pin | Mutation |
| --- | --- | --- | --- |
| `materialise/index.ts` `insertRuns` (226 to 236) | The insert posts to `call_runs?on_conflict=idempotency_key` with `Prefer: resolution=ignore-duplicates, return=representation`. | The in-file check `a second materialisation relies on the durable key and creates no duplicate`. Its stub now answers 409 for a repeated key when the request names no arbiter, as PostgREST does. | Without the arbiter PostgREST targets the primary key, which never conflicts. A repeat materialise then raises 23505, the handler answers 500, and the run the next tick would claim never exists. |

**Evidence, against the shared stack through `ORMA_API_URL`.** `Prefer:
resolution=ignore-duplicates` alone, with and without `return=representation`,
answers 409 `{"code":"23505","message":"duplicate key value violates unique
constraint \"call_runs_idempotency_key_key\""}` on a repeated key. With
`?on_conflict=idempotency_key` the same body answers 201 with `[]`, and a fresh
body answers 201 with the created row including its `id`.

The old request was already wrong before this task. T2.9 surfaces it because the
per-run events need the created rows back, and because the drive repeats a
materialisation to prove nothing is recorded twice.

## 5. Thin details and loose ends, with no kind invented

**`webhook_received` does not name the event id.** The row carries
`{calle_call_id, event_type}` (`calle-webhook/index.ts:300-305`). The winning
event id lives on `call_runs.terminal_writer` as `webhook:<event_id>` (T2.5a) and
on `webhook_events`. A reader cannot join the timeline row to the delivered
event. A redelivery of the same event writes no second row, so the timeline is
unattributed rather than duplicated. The `refetched` row beside it does carry
`outcome`, so the outcome of the delivery is legible.

**`claimed` names the transition and not the invocation.** The detail is
`{state: "claimed"}` (`calle.ts:269`), and the `at` column names when. The claim
RPC is atomic, so only the winning tick reaches the writer. The row therefore
answers "claimed, at this instant" truthfully. It cannot name the tick that took
it, which no pin needs today.

**The dev seed writes a kind outside the vocabulary.** `supabase/seed.sql:132-135`
inserts `call_events` rows of kind `dispatched` and `completed` directly. The
second is not in `CALL_EVENT_KINDS`. The helper rejects that kind for every
caller. That is a seed fixture, and it belongs to T1.6's file rather than this
one. Recorded here so the next reader does not treat the seed as the vocabulary.

**A permanently lost `materialised` append cannot be repaired.** Record 6's
retry covers a transient failure. When every attempt is spent the row is still
lost, because the insert and the events are separate requests. No later
materialise repairs it, because the key is already present and the insert is
ignored. The run stays claimable, so its story starts at `claimed`. A truthful
repair needs a transaction over both writes, or a unique key on
`(call_run_id, kind)` so a repeat append is a no-op. Neither belongs to this
task's paths.

## 6. The append retries twice more before it reports

**Finding M, remediation round 2.** `recordCallEvent` posted once, so a
transient failure lost the row for good and the story stopped before it named
the stop. The measured shapes were a canceled run reading `claimed` alone, a
lost `materialised` row, a failing writer leaving nothing, and a placed call's
story skipping `dispatched`. One dropped request produced all four.

| Where | What | Pin | Mutation |
| --- | --- | --- | --- |
| `_shared/events.ts` `recordCallEvent`, `EVENT_APPEND_ATTEMPTS = 3`, `EVENT_APPEND_WAIT_MS = 250` | The append is attempted three times in total, with a 250 ms pause, and the last error still throws when the budget is spent. The caller may inject the pause as a fifth argument, which the checks use so no test waits. | `retries one lost append and lands the row` and `throws once the append attempts are spent`. Reverting the loop fails both, the first with a single attempt and the second on the attempt count. | One lost request loses the transition for every caller. A canceled run then reads `claimed` alone, and a placed call's story skips `dispatched`. |

**The guarantee, and what it is not.** One lost request no longer loses the
row, and the caller still hears the failure once the attempts are spent. It is
not exactly once. A request that landed while its response was lost appends a
second row, because `call_events` carries no key that could refuse it. The
doc comment states both.

**Overlap with `_shared/finalise.ts`, closed on the orchestrator's decision.**
That module's `appendTimelineRow` also retried `recordCallEvent` three times, so
the two budgets nested and a permanently failing `finalised` append made nine
requests instead of three. The orchestrator widened this task's `owns` line to
`supabase/functions/_shared/finalise.ts` and chose one budget.

The wrapper's retry loop is gone. `abandonRun` and `finaliseRun` call
`recordCallEvent` directly and forward the injected pause, so the append makes
`EVENT_APPEND_ATTEMPTS` requests and the module's `TIMELINE_APPEND_ATTEMPTS` and
`TIMELINE_APPEND_WAIT_MS` constants are deleted. The run-row half stays: a spent
append still travels through `recordAttempt` as the attempt's reason, so
`call_runs.finalise_error` names the loss.

The finaliser's check `a lost finalised append never becomes a second ingest`
now asserts `EVENT_APPEND_ATTEMPTS` and reads three requests rather than nine.
`/tmp/t29/finaliser-count.ts` measures each pass at three requests, where nested
budgets would make nine.

## Every kind against its production caller

`recordCallEvent` is the only TypeScript writer of `call_events`. The SQL
function `public.ingest_call_result` writes `ingested` inside its own
transaction. Both seams are listed.

| Kind | Caller | Code path that reaches it |
| --- | --- | --- |
| `materialised` | `materialise/index.ts` `materialise` (268 to 273) | The scheduler calls `materialise`, which inserts and then appends one row per created run. This task added it. |
| `claimed` | `_shared/calle.ts:269` `dispatchClaimedRun` | `tick` claims through `claim_due_call_runs`, then `dispatchStep` (110 to 124) calls `deps.dispatchClaimed` (159), wired to `dispatchClaimedRun`. |
| `dispatched` | `_shared/calle.ts:392-397` `dispatchOne` | Same path. Recorded after the accepted call is written on the run. |
| `dispatched` | `_shared/dispatch-mode.ts:523-533` `executeDryRun` | Same path, dry branch. `calle.ts:334-337` passes `recordCallEvent` in as the dry event callback. |
| `polled` | `_shared/poll.ts:158` `reschedule` | `tick` selects `duePolls` (246), then `pollStep` (88 to 102) calls `deps.pollDue` (160), wired to `pollRun`. Records a rescheduled pass. |
| `polled` | `_shared/poll.ts:182-187` `pollRun` | Same path. A pending run with no CALL-E call id fails at once. |

Every kind in `CALL_EVENT_KINDS` now has at least one production caller, and no
transition is written twice by two owners for one move. The `dispatched` and
`finalised` kinds each have a dry-run caller beside their live one, and the two
are told apart by `dispatch_mode`.
