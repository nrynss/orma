## Attacks that found nothing more

Each of these is a measurement, not a reading.

* **The repair path, five bad entries in one call.** One extraction carried a blank text, a
  U+0000 text, an out-of-range offset, a retirement of an unowned UUID, a retirement of
  `the museum one`, a free-text `due`, a commitment on an unowned UUID, and an unstorable
  `slot_change_time`. The RPC committed `items 2 mentions 6 retirements 1 commitments 3`, and SQL
  read exactly that with `null_due=1`. The nine-digit fraction `2026-09-15T10:00:00.123456789Z`
  and the lowercase `2026-09-15t10:00:00z` both stored as valid dues. The timeline row carried all
  eight skip reasons. Each bad entry cost only itself.
* **The same item named twice.** Two identical `captured_items` produced two `items` rows with the
  same text and two mentions at offset 44. A retirement and a commitment on one item produced two
  mentions at offset 70. No constraint refuses either. That is a model error the RPC records
  faithfully, and I do not call it a defect.
* **The sanitisation.** Raw, keys and turns all cleaned. The wire held no `\u0000` and no lone
  surrogate. The stored transcript kept `offset_seconds: 3.5` and the empty text. Side note: the
  first reverted run answered `PGRST102 Empty or invalid json`, not `22P05`. A lone surrogate makes
  the JSON body itself invalid on the wire, so the failure lands one layer earlier than round 2
  said. The outcome is the same and the fix is the same.
* **The RPC still raises on unstorable input.** A direct request with `"p_skipped":["a\u0000b"]`
  answered `HTTP 400 22P05 unsupported Unicode escape sequence`. `p_skipped` cannot smuggle a
  U+0000 past the cast.
* **`p_skipped` carries no value.** The reasons are fixed paths and an array index. A commitment
  whose spoken due was the words `call 415 555 0127` produced the reason
  `structured_result.commitments[0].due is not a timestamp`, with no digits and no value.
* **`p_skipped` is not a denial of service.** Through real PostgREST, 1000 entries (58 KB) landed in
  11 ms, 20000 (1.16 MB) in 32 ms, and 200000 (11.6 MB) in 270 ms. The stored detail for the 1000
  entry row was 1125 bytes after TOAST compression and held all 1000 entries. The bound rests on the
  caller, which builds one reason per structured entry.
* **The in-transaction `ingested` row is one unit with the results row.** Two concurrent ingests
  through real PostgREST produced one `already_ingested=false` and one `true`, and SQL read
  `results=1 mentions=1 ingested_events=1`. A client whose response stream failed after the server
  committed lost nothing, and the retry added no second row. A forced failure inside the enclosing
  transaction left neither: after `select 1/0` the run read `scheduled` with `transcripts=0
  results=0 events=0`, while the same transaction had shown `results=1 events=1` a moment before.
* **A run whose first attempt failed validation recovers.** A retirement of an unowned item made the
  RPC raise and left `0 0 0`. The next ingest of the same run landed one transcript, one result and
  one `ingested` row.
* **Case five cannot pass on a mere lock wait.** With `for update` removed, session two still waited
  past one second, because the elapsed check let it through to the row count. The row count then
  failed with `2 2 2 1`. So the wait is not the pin and the rows are.
* **Case eight's six counts, each against a query I wrote.** I kept the case as shipped and added
  independent queries beside it. Mine printed `call_items=5 mentions=1 distinct_join=1
  offset_list=44 commitments=0 retired=1 ingested_events=1`. The case printed `run_items=1
  user_items=5 mentions=1 offsets=44 commitments=0 retired=1`. Every label matches the fact it
  names, and the run's offsets really are the list `44`.
* **Key redaction holds.** The thrown cause kept no key for any of the six shipped spellings, and my
  26 form probe never printed a secret.
* **The ownership read cannot be injected.** `storageRejection` is gone, but every id reaches the
  query only after `UUID_PATTERN` and lowercasing, and the read filters by user as well.

## An observation outside the three files: the shared stack's ACL

The migration's own revokes are correct. A throwaway project built from the committed migrations
reads:

```
MIGRATION ACL {postgres=X/postgres,service_role=X/postgres}
MIGRATION PRIVS ingest_call_result(uuid,...,jsonb) anon=false authenticated=false service_role=true
```

The shared stack reads:

```
acl={=X/postgres,postgres=X/postgres,anon=X/postgres,authenticated=X/postgres,service_role=X/postgres}
anon=true authenticated=true service_role=true
```

The stack's function body matches the migration's body line for line, which I checked by comparing
the text between the dollar quotes. So [INFERENCE] the stack's function was created from the create
block alone and the three `revoke` statements never ran there. This is not a defect in the three
owned files, so it is not a finding. It is a live deployment risk worth naming: the demo stack lets
an anonymous session execute a security definer ingestion RPC. Applying the migration restores the
intended ACL.
