# T6.6 handoff: Operator timeline

Implementation role. This work is ready for independent review.

## What exists now

`/app/timeline` is a browser-rendered owner view under RLS. It reads the
signed-in profile zone, that owner's `call_runs` newest first, and the
`call_events` rows for exactly those run ids, ordered by `(at, id)`.

- The run picker lists only own runs, newest first, as links with `?run=<id>`.
  It defaults to the latest run that has events, falling back to the latest run.
- The selected run header shows the profile-timezone date and time, a state tag,
  a live tag for claimed, dispatched and awaiting_result runs, and a rehearsal
  tag for dry_run runs.
- Each step shows the profile-timezone clock with seconds, the kind in mono
  plum, one gloss line from stable detail fields, and a collapsed JSON detail
  payload with a per-step Show and Hide toggle.
- All eight kinds have gloss lines. Materialised names the scheduled local time,
  finalised names the state and the disposition label, ingested names the counts
  from its detail, and the rest name their own stable fields. Unknown future
  kinds render verbatim and never crash the page.
- Live runs show New steps appear as they happen with a manual Refresh button
  and no timers. Failed and no_result runs appear under A run that stopped with
  their last event kind named.
- Detail payloads render raw JSON with anything shaped like a phone number
  (+ followed by 7 to 15 digits) masked before display.

## Reproducing the failed case on the scratch stack

The seed carries no failed run, so the stopped section needs one ad-hoc row
plus two events. Run this as postgres on the scratch stack after `up`. It
reuses the seed run owner, so the rows land under the signed-in account. No
fixture was committed.

```sql
with owner as (
  select user_id
    from public.call_runs
   where id = '40000000-0000-4000-8000-000000000001'
)
insert into public.call_runs (
  id, user_id, local_date, part_of_day, scheduled_for,
  state, disposition, idempotency_key, dry_run,
  calle_failure, completed_at
)
select
  '4f000000-0000-4000-8000-00000000f901',
  user_id,
  (now() at time zone 'Asia/Kolkata')::date,
  'evening',
  now() - interval '2 hours',
  'failed',
  'not_answered',
  'orma:t66-review:failed-run:v1',
  true,
  '{"failure_code":"408","failure_message":"CALL-E reported failure 408 after dispatch"}'::jsonb,
  now() - interval '1 hour'
from owner;

insert into public.call_events (call_run_id, at, kind, detail)
values
  (
    '4f000000-0000-4000-8000-00000000f901',
    now() - interval '2 hours',
    'dispatched',
    '{"calle_call_id":"call_review_1","state":"awaiting_result"}'::jsonb
  ),
  (
    '4f000000-0000-4000-8000-00000000f901',
    now() - interval '1 hour',
    'finalised',
    '{"calle_call_id":"call_review_1","state":"failed","disposition":"not_answered","item_count":0,"mention_count":0,"retirement_count":0,"commitment_count":0,"failure_reason":"CALL-E reported failure 408 after dispatch"}'::jsonb
  );
```

Clean up with one line. The events go with the run through the cascade.

```sql
delete from public.call_runs where id = '4f000000-0000-4000-8000-00000000f901';
```
