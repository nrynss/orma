## Fix 2, the phone scrub

Thirty five spellings of one synthetic number, driven through the real module against real
PostgREST, whose error body echoes the value it could not cast. The run id carried a spare uuid in
front of the number, so both directions are measured at once: the uuid digits must survive and the
number must not.

* Twenty five spellings mask the whole number, and the spare uuid survives in all thirty five.
  They are the plain, spaced, hyphen, dot, slash, comma, comma space, underscore, parenthesised,
  plus, plus spaced, plus hyphen, country code, non breaking space, narrow no break space, tab,
  newline, digit spaced, digit comma, dot space, comma hyphen, extension, trailing space, `tel:`
  prefix and lone closing paren forms. The extension form masks the number and keeps its own digit.
* Nine spellings leak the number whole. Eight join the groups with an en dash, an em dash, a zero
  width space, a soft hyphen, an apostrophe, a backslash, a colon plus space, or a middle dot. The
  ninth uses fullwidth digits, which `\d` does not match. Fullwidth parentheses leak the first group.

Two spellings a person writes are the en dash and the apostrophe. A word processor converts a spaced
hyphen into an en dash, and the Swiss and Italian conventions write groups with apostrophes. Both
leak under the shipped masker. Finding one records this. The comment above `PHONE_SCAN` claims "any
separator a person writes between them", and that claim is false for the nine leaking forms.

The false mask direction, measured on innocent bodies: a seven digit or longer integer is masked, so
`value 2147483648 is out of range for type integer` reads `value [masked number] is out of range`.
A comma joined list of small numbers is masked too, and so is a compact fourteen digit timestamp.
The module repairs every offset that reaches that integer error, so the masked value is not
reachable through it today. I record the trade off in the residual risk section rather than as a
finding.

* **A stale `poll_unavailable` marker on a completed run.** Row six of my matrix. The contract says

* **The missing finaliser.** `tick` still reports `unavailable("finalisation")`. T2.7a owns that

## Residual risk

* The module's `readOwnedItemIds` failure path throws, which is right, and no shipped test pins it. I
  replaced the throw with an empty set and all ten tests passed. A later change that swallows that
  failure would drop every retirement and commitment as unowned and still commit `valid=true`.
* An extraction naming about 1500 distinct item ids breaks the ownership lookup before the RPC. I
  measured it on this revision through the real module: 500 and 1000 ids built a URL PostgREST
  accepted, 1500 raised `item ownership lookup failed: HTTP 400`, and 2000 raised
  `Invalid URL`. No plausible caller reaches it, because a user owns a handful of items.
* A run that already holds a results row and no `ingested` row can never gain one, because the
  round-2 backfill was deleted and the branch returns before the insert. The local seed's demo run
  is exactly that shape. No production ingest has run yet, and `events.ts` lists `ingested` without
  a consumer, so nothing breaks today.
* The skip reason indexes the caller's extraction, not the repaired result the RPC stores. An
  operator resolves the index against `transcripts.raw.structured_result`, which the same
  transaction wrote.
* `p_skipped` is accepted as any jsonb, so a direct service role caller can store an object there.
  The module always sends an array.
* The RPC validates each of `p_state` and `p_disposition` against its own set and does not check
  that the two agree. The module's mapping is exhaustive and correct, so only a direct caller can
  write a mismatched pair.
* The port probe and `supabase start` still leave a short race window with another process.
