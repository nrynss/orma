### The recorded body equals the live body byte for byte

Both modes ran on run `...0003` with the same stubs, the same briefing and the
same idempotency key. The live path posted the body to the stubbed CALL-E host.
The dry path stored the body it would have sent.

Postgres agrees on the stored copy, read back from `call_events`.

```sql

  from public.call_events
 where call_run_id = '7a000004-0000-4000-8000-000000000003' and kind = 'dispatched'
 order by id desc limit 1
```

### One real call only under the explicit opt-in

The recording fetch saw the request the live path made. The body carried the
rendered task, the inline `result_schema`, the `webhook_url`, and
`metadata.call_run_id`. The recipient appeared as `+1555555XXXX` in every
sample, log line and document.

| Environment | `call_runs.dry_run` | CALL-E requests seen |
| --- | --- | --- |
| `ORMA_DRY_RUN` unset | false | 0 |
| `ORMA_DRY_RUN` unset | true | 0 |
| `ORMA_DRY_RUN=false` | false | 1 |
| `ORMA_DRY_RUN=false` | true | 0 |

The first row is the default that protects a claimed run. The product rule is
that a developer opts in to spending, never out of it, so an unset variable
places no call. The third row is the explicit opt-in, and it placed exactly one
call. The C1 revert below makes the first row place a call, and it fails the
named pin.

A run dispatched dry by the global default reads `dry_run = false` in SQL. That
is the reviewed design. The column records an operator's per-run override, and
the contract change records the same reading.
