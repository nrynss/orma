## The attacks

**A run with a null `calle_call_id`.** R5. Reported above as finding two. The run is never
finalised, makes no CALL-E request of its own, and stays queued across ticks.

**A payload CALL-E reports as still running.** R6. `ingestTerminalRun` refuses the state before any
write. The run keeps `completed_at null` and has zero events, zero transcripts and zero results. The
next tick re-fetches it again (`1 then 2`). Nothing is written for a call that has not finished.

**A payload whose ingestion is rejected.** R7. The stub answers the RPC with a 400. The rejected run
keeps no partial state, writes no event and does not land. Its sibling finalises in the same tick.
Across three ticks the RPC sees `4` attempts for that one run and the run never leaves the queue.
That is the unbounded case of finding one.

**Two overlapping ticks.** R8. Two `tick` calls run under one `Promise.all` over one terminal run.

counts its own step as landed, because its ingest returned `already_ingested` and the step ran to
completion. The `TickResult` comment defines a landed step that way, so I do not call it a defect.

**A run whose ingestion succeeds but whose timeline write fails.** R9. Reported above as finding

## Residual risk

- **No live CALL-E re-fetch.** Every payload in this round came from a stub serving the recorded
  fixtures. A live call is evidence, not a gate, and `CALLE_API_BASE` stayed the stub host.
- **A race can double count one run.** The tick that loses a finalise race still counts its step as
  landed, because the step returned a summary. The `TickResult` comment defines a landed step as one
  that ran to completion, so I do not call it a defect. An operator who sums those numbers over a
  minute can still read them as more runs than there were.
- **`no_result` cannot happen.** `terminalRuns` selects the state, and no writer in the repository
  writes it. `answered_no_result` is a disposition. The extra state is harmless and I do not report
  it.
- **The finaliser records no `refetched` row.** T2.9's list of transitions names `refetched`, and the
  webhook writes one. A poll-terminalised run reads `polled,ingested,finalised`. T2.9 owns that
  judgement.
- **The dry path writes a different `finalised` detail.** `dispatch-mode.ts:549` puts the provider's
  free text into `failure_reason`, where the finaliser deliberately puts the code. Both satisfy the
  `call_events` contract, and `dispatch-mode.ts` is T2.8's path, so I only note the difference.
- **An `already_ingested` replay whose `completed_at` is null never recovers.** R11 measured it. The
  RPC sets `completed_at` in the same transaction as the `results` row, so no path in the repository
  can reach that state. It stays a robustness note rather than a finding.
