## What I tried to falsify

**A completed fixture names captures, retirements and commitments with no call
to action.** The new test spreads `call-completed.json` and adds a retirement
and a commitment. It asserts the text carries `Continental`, `book the dentist`
and `send Amma the photos`, carries no raw id, and trips no CTA marker. The
resolver supplies the commitment text, and `formatPostCallMessage` renders the
`Committed` section only when the list is non empty. Reverting the commitment
resolution drops `send Amma the photos` and the test fails. Reverting the format
push drops the section and the sibling test fails.

**An invalid result still sends an honest receipt with no raw uuid.** The null
fixture test and the malformed-object test both land on `sent`. Each one asserts
the text carries no raw id and no failure word. The malformed object keeps a
retired id and a committed id but its resolver returns null. So both lists stay
empty and the text reads `Captured: none` and `Retired: none`. Reverting the
guard that returns an empty list for a non array would push a value into the
text and break the assertion.

**No call to action.** `containsCallToAction` runs on the assembled body in
`deliverPostCallTelegram` with `enforceNoCta: true`. The commitment line reaches
the same guard as the other two. A question mark in any resolved text would
throw. That behaviour predates this commit and the new line rides the same path.

**Commitment ids resolve to items.** The ingest migration validates each
`commitments[].item_id` against `public.items` for the same user. So a resolver
built on `items` can name a commitment. The reuse of `resolveRetiredText` for
commitment ids is therefore sound, not a type error.
