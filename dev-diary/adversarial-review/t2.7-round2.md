## Specific attacks that found nothing more

* **Ownership read race.** The RPC re-checks ownership under its own statement, so the REST read cannot let a foreign
  write through. An item deleted between the read and the RPC raises, and the retry marks the result invalid. I could
  not bypass the `in.(...)` filter, because `storageRejection` runs first and only canonical UUIDs reach the query.
  The check belongs in SQL anyway, as finding one says.
* **Foreign item id.** `valid=false` does not hide the write. Run `d008` left user B's item `open`, and
  `results.error` names the path. The disposition discards the rest of the call, which finding one covers.
* **`due` validator, under-rejection.** I found no value the regex accepts that PostgreSQL refuses. I checked
  `+15:59`, `-1559`, year 0001 with `+15:59`, year 9999 with `-15:59`, leap days, and six fraction digits.
  `+16:00`, `+15:60`, `2026-02-29` and `1900-02-29` fail in PostgreSQL and in the regex alike.
* **Key redaction.** Service key, JWT and `sb_` redaction held in every probe.
* **Port probe.** It covers every rewritten port on both address families. The revert fails the script.

## Residual risk

* The `already_ingested` summary echoes the retry's `p_structured`, not the stored result. A retry that newly fails
  validation returns `slotChangeRequested: null` for a run that asked for a change.
* A foreign item id and a hallucinated one produce the same reason. An operator cannot tell a briefing leak from a
  model error without a second query.
* The port probe and `supabase start` still leave a short race window with another process.
* Transcripts could exceed PostgREST's request size limit. I did not probe that limit.
