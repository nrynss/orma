* **`p_skipped` as an injection vector.** A list holding `a\u0000b` raised with
  `\u0000 cannot be converted to text` and left zero rows. A list holding
  `'); drop table public.items; --` stored that string verbatim in the event, and the items table
  kept its 8 rows. The module builds every reason from a fixed path and a caller index, so it can
  produce neither shape.
* **`p_skipped` as a size vector.** 100000 reasons stored 5688895 characters of jsonb as 454164
  bytes in one event row, in 107.8 ms. The list the module can build is one reason per extraction
  entry, so the bound rests on the payload the caller already holds.
* **`p_skipped` as a shape.** A direct caller passed `{"not": "an array"}` and the event stored an
  object. The module always sends an array.
* **The ownership read.** Four ids shaped as `uuid)&select=*`, a quote, a double quote and a
  `")&user_id=eq....` suffix built zero lookup URLs, and only the canonical id built one. That URL
  filters by user and id. A hostile user id is percent encoded, so `)&select=*` travelled as a
  value. Real PostgREST answered 400 with the whole encoded value inside the uuid error for the
  hostile filter, which shows the filter never split, and 200 for the canonical one.

## Candidate findings I judged false positives

* **The bare eight digit date survives.** A run of eight digits grouped four-two-two that spells a
  valid date is a value this module would store, so it keeps its digits. The Deno row
  `2026-09-12-###-###-####` pins the same behaviour for a date beside a number. Documented and
  pinned, so not a defect.
* **A date-shaped front of a longer number keeps eight digits.** The number does not leave whole,
  and the digits that survive belong to a value the module stores. Residual risk, not a finding.
* **The failureCause join masks the error code when the message starts with a digit.** The primary
  rule masks a run of seven or more digits joined by separators. The join makes one such run. Benign
  over-mask.
* **The status sentence.** `failureCause` reads `response.status`, which is always a three digit
  code. The comment's "ours" reads as shorthand for "not response body text". I judge it a false
  positive, and I found no reachable behaviour it misdescribes.
* **Zero counts on an `already_ingested` summary.** The race above returned one `true` with four
  zeros, which is what that call wrote. Rounds 1 to 5 read it the same way.
* **A fully repaired extraction reads `answered_extracted` with zero rows.** Every entry was schema
  valid and dropped for a value reason, so `valid` is true. The skip list explains it and the
  disposition table keys on the result being non null.
* **The missing finaliser.** `tick` still reports `unavailable("finalisation")`. T2.7a owns that
  join.

## Residual risk

* The masker cannot tell a number from a count. A long integer, a version and a clock time with a
  fraction all lose their digits from an operator message. So do money, a fraction, a comma joined
  count list, a compact stamp and a date-shaped run it does not store. The comment states this and I
  measured every shape.
* The letter exclusion also leaks a run broken into short pieces, for example `415a555b0127`, and
  a superscript or a Roman numeral breaks a run the same way. Finding one covers the letter family.
  I record the rest as the stated exclusion.
* A timestamp followed by a hyphen and four digits is not a storeable timestamp, because the scan
  reads `-dddd` as a zone offset. The whole run then masks, which is an over-mask and not a leak.
* `readOwnedItemIds` has no pagination. PostgREST's row limit is 1000, and round 4 measured 1500 ids
  raising `HTTP 400` on URL length. Between those points an owned id beyond the page would read as
  unowned and its retirement would be dropped with a wrong reason. [INFERENCE] I did not re-measure
  it this round.
* The RPC checks its own set for `p_state` and `p_disposition` but never checks that the two agree.
  The module's mapping is exhaustive, so only a direct caller can write a mismatched pair.
* `spec.md:216` lists `no_result` in the terminal state set. Nothing writes it. The webhook maps the
  re-fetched status, the RPC accepts three states, and the finaliser's queue filter reads it
  defensively. [INFERENCE] from the code, not measured.
* `p_skipped` is accepted as any jsonb and is unbounded, so a direct service role caller can store
  an object or 454 KB in one event row. The module always sends an array of one reason per entry.
* `runId` and `userId` are checked for a non empty string only, so a malformed pair becomes a
  PostgREST cast error rather than a module error. The cause is scrubbed, and the shipped callers
  pass database uuids.
* A failed payload that still carried a structured result would write items and mentions for a
  `not_answered` run. `spec.md:351-353` makes the pair mutually exclusive, so the path needs a
  contradictory payload.
* The local seed's demo run holds a results row and no `ingested` row, so the RPC reports
  `already_ingested` and writes nothing. No production ingest has run yet. Round 5's note, unbuilt
  here.
* The stale `poll_unavailable` marker on a completed run stays unreachable, because `poll.ts` writes
  that code only when the run has no call id and no re-fetch exists without one.
