## False positives I rejected

**A missing named key yields 500, not 401.** When `SUPABASE_SECRET_KEYS` lacks a `materialise`
entry, the package raises a configuration error and the function answers 500. Probed. No read
reaches the handler, so it fails closed either way. The landed materialise handler behaves
identically, so this is an inherited platform property and not a T7.3 defect.

**Serial profile processing against the 150 second wall clock and 2 second CPU budget.** The
run walks profiles one at a time. The Vertex token exchange signs a JWT per attempt, which is
the approved T7.2a cost. Whether the budget binds depends on a profile count nobody can name
today. A demo-scale run finishes far inside the limits, so the impact is not provable.

**A same-week manual re-run would duplicate a report and its emails.** There is no uniqueness
guard on `pattern_reports` for a period. The shipped trigger is one weekly pg_cron schedule with
no retry path, so no shipped code path produces the double delivery. The AGENTS double-dial rule
governs CALL-E dispatch, which materialise enforces twice over.

**A Resend 200 with a non-JSON body would be recorded as failed though mail likely went out.**
The parse throws and the catch marks the row failed. Triggering it needs Resend to violate its
documented response. The landed Telegram seam carries the same tolerance and was approved.

**A failed error patch after a failed send leaves the row without outcome text.** The row still
exists and the caller still sees `failed`. The code comments name this as deliberate, and the
bookkeeping is best effort on both channels.

**Telegram prepends a "Pattern report" header line to the prose.** The P3 handoff orders T7.3 to
call `deliverPatternTelegram` and never rewrite it. The seam owns formatting and carries the
prose itself as written. Both channels deliver the same validated text.

**RESEND_API_KEY and RESEND_FROM are new requirements missing from the env lists.** They are not
missing. `.env.example` lists both under the T5.1 email section, and
`.github/workflows/_env-example.yml` carries both names already.

## Done-when

- "A scheduled run delivers to both channels." The handler stores the validated report, then
  calls `deliverPatternTelegram` and `deliverPatternEmail` with the same prose. Both paths are
  pinned through injected fetches at the real endpoints.
- "Respects each channel's toggle." Each helper reads its own column and skips inside itself,
  before any auth read on the email side. Probed in both directions.
- "Records success and failure distinguishably." A row is inserted before each attempt. Success
  sets `sent_at` with a null `error`, failure sets `error` with a null `sent_at`. A bookkeeping
  patch failure never rewrites a real send outcome.
- "Pin Telegram by calling `deliverPatternTelegram` with fixture prose and counting the
  `deliveries` row outcome." The committed suite does exactly this, and my run confirms it
  passes.

Every named seam holds against the real schema and the T7.3 done-when. The verdict is APPROVE
with zero findings at every severity.
