## Design choices

**H, a re-fetch that fails past the window.** The poll gives up with `poll_timeout`, as it would on a pending re-fetch. The failure message carries the re-fetch error, and the `polled` row carries `outcome: refetch_failed`. Retrying forever would unbound the window that requirement 3 promises, and round 1 already closed one immortal row. The cost is a CALL-E outage that outlasts the window. Such an outage can record a completed call as failed. The message names that cause on the run, so an operator can tell it from a call nobody answered.

**First L, attribution on a redelivery.** Reordering the writes cannot fix this. A failure between the PATCH and the `refetched` insert still leaves a redelivery that matches zero rows. Only two writers move a pending run. Every poll write to a terminal state records a `polled` row naming that state. So a run holding the re-fetched state with no such row was moved by this event's earlier attempt. The check runs only on a 409, which keeps first deliveries free of extra reads. It also keeps the poll-first race from reading a `polled` row the poll has not inserted yet.
