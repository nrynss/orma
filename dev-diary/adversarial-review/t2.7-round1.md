## Findings

| `_shared/ingest.ts`, the validation step around `parseStructuredResult`, and the casts in `20260912180000_ingest.sql` | The parser accepts values the RPC rejects, and a rejected RPC kills the whole ingest. The invalid path never runs. `commitments[].due` accepts any string, and the shipped schema invites free text there, `in their own words`. The SQL casts it to timestamptz. A non-UUID `item_id` or a blank captured `text` behaves the same. The module promises that an invalid result still writes the transcript, a disposition and `answered_no_result`. For this class the promise is false. The transaction rolls back to zero rows. The run keeps `state='awaiting_result'` with no disposition. The CALL-E payload is immutable, so every retry fails the same way and the run never finalises. Fix in `ingest.ts`: after parsing, reject any result with a blank captured text, a non-UUID `item_id`, or a `due` that fails `Date.parse`. Send it through the same `valid=false` path as a parse failure. | Live drive against the harness. A valid-shaped result with `due="next Tuesday after work"` made `ingestTerminalRun` throw. SQL then showed the run still `awaiting_result` with 0 transcripts, 0 results, 0 mentions, 0 commitments and 0 events. The paraphrased `item_id="the museum one"` reproduced it identically. | Reverting the fix keeps a live pipeline poison pill. The schema invites free-text dues, so the first caller who says `next Tuesday` freezes that run's ingestion forever. No transcript, no disposition, no fallback for the receipt. |

## The strongest attacks and why they found no more

* Counts are computed, never invented. The RPC increments each counter exactly where it inserts
  or updates. The retirement update raises when not found. Returned counts equalled my SQL
  counts on the happy path, the duplicate and the invalid path.
* Unoffset retirement raises and leaves nothing. Pinned twice, by the shipped script's case four
  and by my cross-user retirement that raised after a captured insert in the same transaction.
* Exactly-once survived a duplicate ingest and a genuine race. The lock serialises the second
  reader before the results probe. No duplicate items, mentions, commitments or retirements
  appeared, and no second `ingested` event was written.
* The privilege surface is correct as measured in SQL. `has_function_privilege` returns false
  for `anon`, `authenticated` and `public`, true for `service_role`.

## Residual risk I could not close

* The boundary between `parseStructuredResult` and the SQL casts is the load-bearing wall for
  finding one. `result.ts` is not owned by T2.7, so `ingest.ts` must stay stricter than SQL on
  its own. If remediation tightens the parser instead of `ingest.ts`, the next schema change can
  reopen the gap silently.
* The harness ships only the service role key, so I pinned the RPC privilege in SQL rather than
  over HTTP with a real anon key. The HTTP path through PostgREST for `anon` is unverified.
* A direct service-role caller can still send shapes TypeScript would reject. For example a JSON
  null `evidence_offset_seconds` lands a mention with a null offset. No such caller exists
  today, and the grant is service role only.
* Offset seconds have no range check on either side, so negative offsets land. Cosmetic today.
* `ingestTerminalRun` has no production caller yet. Poll and tick wiring arrives later, and the
  retry semantics behind finding two depend on how that wiring handles a throw.
