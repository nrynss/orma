# T2.5 contract change

T2.5 must close a gap in a task that already landed. The landed T2.6 receiver
re-fetched the authoritative call and recorded that it did so, but it never
moved the run out of `awaiting_result`. T2.5's own done condition says the poll
is a no-op once the webhook wins, and that condition was unreachable while
nothing wrote the terminal state.

| Where | What | Pin | Mutation |
| --- | --- | --- | --- |
| T2.5 ownership | Add the run-state transition to `supabase/functions/calle-webhook/index.ts`, and add `supabase/functions/_shared/poll.ts` plus the poll wiring in `supabase/functions/tick/index.ts` to T2.5. | A matched terminal delivery leaves `call_runs.state` at `awaiting_result` and `poll_after` untouched, so the poll re-fetches a run the webhook already resolved. The transition is a `PATCH` guarded by `state=in.(dispatched,awaiting_result)`, and exactly one of the two writers matches. | Removing the receiver's transition makes the webhook decorative and every terminal run reaches `completed` by polling alone, which costs a full give-up window. Removing the guard in either writer lets both move one run, so a late poll can overwrite the webhook's authoritative state. |
| T2.5 event kinds | Reuse the existing `polled` kind from `CALL_EVENT_KINDS`. No new kind is added. | `supabase/functions/_shared/events.ts` already lists `polled`, and `assertTerminalDetail` constrains only `finalised`. | Adding a second kind for the same transition splits the timeline an operator reads. |
| T2.9 dependency | The poll sets a terminal `state` and leaves `completed_at` null. | `tick/index.ts` selects `terminalRuns()` as terminal states with `completed_at is null`, and hands them to `deps.finalise`. A poll that set `completed_at` would remove the run from the finaliser's work queue before ingestion ran. | Setting `completed_at` in the poll skips finalisation and ingestion, so the run completes with no transcript, no result and no items. |
| T2.5 round 3, findings 1 and 2. A new migration adding a column to `call_runs` (owner for the migration to be assigned by the orchestrator), plus T2.5's writers in `supabase/functions/calle-webhook/index.ts` and `supabase/functions/_shared/poll.ts`. | Add a nullable `call_runs.terminal_writer text`. Every guarded pending-to-terminal PATCH sets it in the same UPDATE as `state`. The webhook writes `webhook:<event_id>`. The poll writes `poll` on its terminal, give-up and missing-call-id writes. On a zero-match PATCH the receiver reads `terminal_writer`. It records `applied` only when the value equals its own tag, and `already_resolved` otherwise, including null. `earlierAttemptApplied` and the `redelivered` flag go away. No schema-free design is truthful. No existing column can hold an event id without misusing another task's contract. A record on `webhook_events` or `call_events` is a second REST write, and PostgREST offers no transaction across two writes. An invocation killed between the PATCH and that record leaves a terminal run with no record. The `REFRESH_LEASE_MS` reclaim then retries it as a redelivery. A poll whose `polled` insert failed leaves the same picture. The redelivery cannot tell these apart, so either binary outcome is false in one of them. The owner-read RLS policy on `call_runs` would expose the event id to the run's user. An event id is a de-duplication key, not a secret, but the owner should confirm that. | Pins F1a, F1b and F1c in `t2.5-round3.md` fail today. Once the column exists, a unit pin serves a zero-match PATCH and a run whose `terminal_writer` names another event, and expects `already_resolved`. The same pin with this event's own tag expects `applied`. A live pin raced in both orderings reads `terminal_writer` by SQL. It must name exactly the writer whose timeline row claims the transition. | Dropping the column from either writer's PATCH leaves it null, so a redelivery of the winning event records `already_resolved` for its own write. Comparing only the `webhook:` prefix, not the full event id, lets a second event claim the first event's write again, as in F1a. |

The last row above is not applied to T2.5. On 2026-09-13 the user made it a new task, T2.5a, in `PHASE-2-call-engine.md`. T2.5a owns the migration and the writer changes. The row stays here as the design record.
