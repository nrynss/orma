## Findings

| Where | What | Pin | Mutation |
| --- | --- | --- | --- |
| `supabase/migrations/20260914110000_phone_confirmations.sql:63-78` | **H1: A code remains valid after a number is changed away and then changed back.** The verifier only compares the stored number with the current profile number. Start confirmation for A, change the profile to B, change it back to A, then submit A's original code. The row still qualifies and confirms A. The required changed-number guarantee is that no pre-change code can confirm after a number change. Invalidate pending confirmations when the profile number changes, or bind the verifier to a confirmation generation that changes with every profile update. | A local database pin starts an A confirmation, changes A to B and B to A through the authenticated profile route, then calls `verify_phone_code` with the original code. It must return `false`, leave `phone_confirmed_at` null, and leave the row unconfirmed. This fails today by inspection because the only predicates are `phone_e164 = v_phone`, state, and expiry. | Revert the pending-confirmation invalidation or generation binding. The A to B to A pin confirms the stale code again. |
| `supabase/functions/confirm-phone/index.ts:66-71`, `supabase/functions/_shared/calle.ts:84-94` | **M1: Dry run records no masked confirmation request, and the provided masker would retain the code.** `dispatchPhoneConfirmation` returns `requestBody`, but the caller discards it. No confirmation event or other audit record is written. This misses the explicit dry-run record requirement. Further, the generic request masker masks the recipient and webhook secret, not the six code digits embedded in `task`. Recording that value would violate the code-secrecy requirement in production if this path were reused. | A dry-run handler pin should observe one durable confirmation dispatch record whose request has the phone and webhook secret masked and whose task contains no six-digit code. A production-mode variant must observe neither the response nor any record contains the code. The current handler performs no record write after dispatch, while `buildConfirmationCallRequest` places the raw code in `task`. | Revert the confirmation-specific redaction or the durable masked-record write. The dry-run pin either finds no record or finds the original code. |
