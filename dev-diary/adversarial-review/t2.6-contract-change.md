# T2.6 delivery blocker

CALL-E's current official webhook documentation resolves the inbound contract.
Each JSON event has `id`, `type`, `created_at`, and `data`. The
`CALL-E-Event-Id` header must equal `id`. The authoritative call identifier is
`data.id`. Only `call.completed`, `call.failed`, and
`call.result_validation_failed` are terminal event types.

The local receiver implementation follows that contract and re-fetches
`GET /v1/calls/{data.id}` before any later transition. Its three
`*.documented.json` fixtures are explicitly documentation-derived. They are
not recorded CALL-E deliveries and must never be represented as such.

| --- | --- | --- | --- |
| `call_sY36Xr07vuAsq0RmsGOX7A` | A webhook-enabled control call rang, was answered, and completed. The deployed endpoint recorded no event. The provider event stream contained its terminal call event, but no delivery record. | Receive an actual provider POST at the deployed endpoint, with matching header and body id. Capture each terminal shape with numbers masked. | The provider accepted `webhook_url` but did not deliver. A documentation fixture cannot prove live delivery or retries. |
| `supabase/functions/calle-webhook/index.ts` | Local implementation checks the path secret, header and body id, terminal type, and `data.id`. It re-fetches with the bearer key and ignores body metadata. | Independent review, then deploy the reviewed function. | The currently deployed function is the earlier capture-only receiver. |
| CALL-E webhook service | Official docs state per-request `webhook_url` receives terminal events and retries non-2xx responses. The successful control call produced neither observed POST nor retry. | CALL-E must explain or repair the missing delivery, or a later control call must provide the missing evidence. | Polling can reconcile a terminal call, but it cannot satisfy the webhook proof or provide real webhook fixtures. |

T2.6 cannot close until an observed provider delivery proves the live boundary.
