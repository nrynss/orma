## Findings

| H1 | H | `.github/workflows/keepalive.yml`, `Keep Supabase active` | `curl --fail` rejects only HTTP status 400 and above. It exits successfully for a 201, 204, or 3xx response. T8.2 requires the job to fail on every status other than exactly 200. A proxy regression that returns a redirect or an empty success response therefore reports a healthy keepalive and hides the failed probe. | Run the exact curl flags against a local endpoint returning 204 or 302. It exits 0. The step must instead capture `%{http_code}` and fail unless it equals `200`, while suppressing the response body. | Replacing an exact status comparison with `--fail` restores green jobs for non-200 responses. |
| M1 | M | `.github/workflows/keepalive.yml`, workflow and job scope | The workflow declares no `permissions`. Its `GITHUB_TOKEN` rights therefore follow the repository or organization default, which can grant write access. `actions/checkout` needs only this repository's contents read permission. The backup push already uses the separately scoped fine-grained token. | Inspect the workflow for a top-level or job-level `permissions` map. None exists. Add `permissions: { contents: read }`, then confirm the checkout and explicit backup-token push still work. | Removing the explicit read-only permission returns the token to the mutable repository default. |
