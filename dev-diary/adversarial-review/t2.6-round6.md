## Verified non-issues

The reclaim filter is
`or=(type.eq.pending,and(type.eq.refreshing,received_at.lt.ISO))`. The ISO
timestamp is unquoted and contains a dot and a colon. I checked the PostgREST
parser. A logic leaf value is `many (noneOf ",)")`, so the parser accepts both
characters inside a tree. Only a comma or a paren needs quoting. The filter is
valid.

The claim is one conditional PATCH. Postgres evaluates it on the row under a
row lock, and the body moves `received_at`. A synchronized duplicate therefore
sees a fresh `received_at` and loses. Exactly one caller re-fetches.

## What I could not pin

First, no test observes the claim's `received_at` update. I removed
`received_at: new Date(now).toISOString()` from the claim body in
`/tmp/t26r6/index.gap1.ts`, and all 16 tests still passed. The pin's mock does
not re-check the row after it applies the body, so it cannot see the anchor
move. If someone reverted that field, the lease window would start at insert
instead of at claim. The impact is small, because insert and claim are
adjacent, so I do not raise it as a finding. The code is correct today.

Second, no in-file test drives the `!hasMatchingOrmaRun` rejection. Every
`call_runs` mock returns one matching row. Round 4's external probe covered
that branch, and removing the ownership check does fail a pin, so the property
is not left open. A direct mismatch rejection pin would still be stronger.

Third, I cannot prove how long CALL-E retries. A row stranded in `refreshing`
recovers through a later delivery only after the five minute lease. If the
provider stops retrying inside the lease, the row stays `refreshing`. Polling
reconciles the call, so I do not raise it. Round 5 recorded this residue, and
it is pre-existing.

Fourth, the external delivery gap stays outside the receiver. The deployed
endpoint has never received a provider POST. I judge the receiver's own
correctness only, as instructed, and I do not score the gap against this round.
