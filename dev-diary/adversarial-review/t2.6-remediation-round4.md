## M1 design

The claim is one conditional PATCH. Its filter is
`event_id=eq.X&or=(type.eq.pending,and(type.eq.refreshing,received_at.lt.CUTOFF))`.
Postgres evaluates it on the row under a row lock. The body sets
`received_at` to now, which leaves the stale window. A second caller that
evaluates the same row after the first commits finds `refreshing` with a fresh
`received_at`, so it matches nothing and loses. A fresh concurrent duplicate
therefore still produces exactly one re-fetch. The existing tests
`a duplicate terminal event is a no-op and does not re-fetch` and
`a re-fetch failure releases the event so a retry can win` keep passing.

## M2 failure decision

A failed timeline write fails the webhook with 500. The inner catch already
releases the claim back to `pending`, so the provider retries and can still
write the rows. A 200 would tell the provider the event is done, and the lost
transition row would never be written again, because the provider does not
redeliver a handled event. The retry can write `webhook_received` twice when the
second append fails, but `call_events` is an append-only timeline and a
duplicate row is recoverable where a missing row is not.

The receiver writes both rows before it marks the event `refetched`, so a
partial write never leaves the event in a terminal state.
