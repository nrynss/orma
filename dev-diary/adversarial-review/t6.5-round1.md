## Scope and evidence

I read `AGENTS.md`, the T6.5 specification, the T6.5 handoff, the approved
T6.7 migration review, the core schema, the owner RLS policies, and the
Settings implementation. I did not modify implementation, migration, type,
or status files.

`cd web && npm run check` passed with zero Svelte errors or warnings. `cd web
&& npm run build` completed successfully. The static scan found no direct
`call_runs` write and found cancellation and deletion only through
`cancel_call_run` and `delete_my_account`.

The profile, consent, slot, and scheduled-run reads include the authenticated
user id. RLS independently constrains every table operation to that owner.
Telegram state also uses the same session-derived user id, anon key, and
Bearer token. Existing widget attach, mint, and unlink calls remain present.

Consent grant inserts the required outbound row with the displayed wording.
Consent revocation updates every live outbound row. The dispatcher therefore
sees no live consent on its next tick. Pause and resume update every owned
slot, while slot edits preserve the selected weekdays and derive part of day.

The today filter compares each scheduled run's stored local date with the
current date in the selected profile timezone. Cancellation calls the T6.7
owner RPC and removes the row from local state only after a successful result.
The RPC's lock and scheduled-state check provide the dispatch race boundary.

Deletion requires the literal `DELETE` confirmation, explains the cascade,
calls the T6.7 owner RPC, signs out, and redirects home. The approved RPC
deletes caller-owned audio before auth cascades remove relational rows.
