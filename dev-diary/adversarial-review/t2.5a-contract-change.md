# T2.5a contract change

T2.5a adds `call_runs.terminal_writer` and needs no contract change. Two
records belong here: the writers the column covers and the owner-read decision
under `call_runs_owner_read`.

## Scope: the writers the column covers

`_shared/calle.ts` also writes terminal states, in `refuseRun` and on a failed
dispatch. Those writes are unguarded, so no state filter constrains them. They
also set `completed_at`, so the tick's finaliser never revisits them. No
webhook follows a refused dispatch or a CALL-E 409, because no call exists.

The column therefore stays null for those runs. A webhook or poll that matches
no row on such a run records `already_resolved`. That is truthful, because
neither writer moved the run.

`terminal_writer` covers the one guarded transition two writers compete for.
Widening it to every writer of a terminal state would need `_shared/calle.ts`.
T2.5a does not own that path, and no acceptance pin needs it.

## RLS decision: the owner may read the column

**Decision.** The owner reads `terminal_writer` through the existing
`call_runs_owner_read` policy. The migration changes no policy and no column
privilege. The migration header records the same decision beside the column.

**Reasoning.**

- A row-level select policy grants the whole row. Carving one column out is a
  privilege question, not an RLS question, so the policy cannot do it alone.
- Supabase grants `select` on the whole table to `authenticated` by default. A
  revoke would name every other column, and the next added column reopens the
  gap silently.
- The value is a CALL-E event id such as `evt_...`. It is a de-duplication key
  and not a credential. It carries no secret and no phone number.
- The owner already reads the run row and its `call_events` rows. The stored tag
  reveals no class of data the policy does not already expose.

| Where | What | Pin | Mutation |
| --- | --- | --- | --- |
| `supabase/migrations/20260913120000_terminal_writer.sql` | Leave `terminal_writer` readable by the run owner under `call_runs_owner_read`. | The psql transaction below reads one row with the stored tag as the owner, and zero rows as a second user. | Revoking `select` on the column makes an owner read of the tag fail on a permission error. The row policy then disagrees with the column it grants. |

**Pin, as run.** The transaction inserts one marker run, assumes the
`authenticated` role twice with different `sub` claims, and rolls back, so it
leaves no row.

```sql
begin;
insert into public.call_runs (id, user_id, local_date, part_of_day, scheduled_for, idempotency_key, terminal_writer)
values ('2a5a0000-0000-4000-8000-000000000001','00000000-0000-4000-8000-000000000001','2026-09-13','t25a-rls-pin', now(), 't25a-rls-pin-1', 'webhook:evt_pin');
set local role authenticated;
set local request.jwt.claims = '{"sub":"00000000-0000-4000-8000-000000000001","role":"authenticated"}';
select 'owner' as actor, count(*) as rows, max(terminal_writer) as tag from public.call_runs where id = '2a5a0000-0000-4000-8000-000000000001';
reset role;
set local role authenticated;
set local request.jwt.claims = '{"sub":"00000000-0000-4000-8000-0000000000ff","role":"authenticated"}';
select 'other' as actor, count(*) as rows from public.call_runs where id = '2a5a0000-0000-4000-8000-000000000001';
reset role;
rollback;
```

Observed output against the shared stack on 2026-09-13:

```text
 actor | rows |       tag
-------+------+-----------------
 owner |    1 | webhook:evt_pin
 actor | rows
-------+------
 other |    0
```

The owner sees one row and the tag. The second user sees no row.
