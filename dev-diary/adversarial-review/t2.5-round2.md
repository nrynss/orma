## Requirement check

1. **Bounded give-up window.** It holds for runs with and without `dispatched_at`, which pins M and A confirm. The window's gate overrides an authoritative terminal state. See the H finding.
2. **One pass per tick.** `tick()` calls `pollDue` once per due run. `pollRun` makes at most one re-fetch and never loops. Pins H and M confirm this.
3. **Per-run isolation of poll and finalise.** `pollStep` and the finalise loop each catch per run. Pin H answered 200 with the sibling polled. The tick's reported counts overstate success. See the second L finding.
4. **Exactly one winner between webhook and poll.** Six raced rounds, three in each ordering, each ended with one winner. The loser's guarded PATCH matched zero rows and changed nothing.
5. **State from the re-fetch only.** The webhook body type never reached `state` in any pin. The give-up gate writes `failed` without a re-fetch. See the H finding.
6. **No timeline row asserts a state that did not land.** A losing poll writes no row, and a losing webhook writes `already_resolved`. A retried webhook misattributes its own write. See the first L finding.

## Residual risk

- **Live timing proof.** The T2.5 done condition still needs a real CALL-E key. It asks for one live call through polling alone and one run the webhook won. This round placed no real call. A live call is evidence, not a gate, so this is not a finding.
- **Overlapping ticks.** `duePolls` takes no claim. If one tick outlives the one-minute cron, two ticks can poll the same run. The guard still yields one terminal winner. A pending run could gain two `polled` rows and two re-fetches. I did not pin this.
- **Timeout fallback clock.** `created_at` marks materialisation, not dispatch. A row without `dispatched_at` materialised early fails on its first pass. No in-repo writer produces that row today.
- **Timeout leaves `poll_after` set.** Pins M and A read `poll_after` non-null on a `failed` run. `duePolls` filters on state, so nothing polls it again.
- **Webhook transition omits provider detail.** The webhook's write sets only `state` and `poll_after`. The poll also writes `calle_failure` and `calle_confidence`. T2.7a re-fetches before ingestion, so this depends on T2.7a doing that.
- **`refetched` keeps `state` beside `outcome`.** T2.9 must read `outcome` before it trusts that state.
