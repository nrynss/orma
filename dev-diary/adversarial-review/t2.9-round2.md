## Judgements on the contract-change records

**Record 1, delivery is the `deliveries` table and not a ninth kind.** Agreed.
`_shared/deliver-telegram.ts:214-221` inserts into `public.deliveries` and
writes no `call_events` row. That table carries `call_run_id` with a foreign
key, so the receipt joins to the run. The kind list in the phase document ends
at `finalised`, and the contract forbids a ninth kind, so the reading is the
only one available. My ordered reads show the completed run ending at
`finalised`.

**Record 2, the four `finalised` writers and no row at handover.** Verified.
Each path writes the run first and appends once. The 409, the rejection and the
stranded recovery each read one `finalised` row. The handover reads `claimed`
alone, and the next tick continues to `claimed, polled, ingested, finalised`.
The design choice that the handover writes no row is defended. Putting a row on
that path fails `a stranded run that recorded a call id is handed to the poll`
with `a run handed to the poll must record no finalised row`.

**The four writers set `completed_at`, which the contract says ingestion owns.**
Judged correct, and load bearing. Reverting `completed_at` from the refusal
write gives one move two `finalised` rows, `refused` then `abandoned`, because
the finaliser's queue selects a terminal run with a null `completed_at`.

**Record 3, the failure shape and no new tag.** Agreed, except the sentence the
L finding names. Every state the four writers record matches
`/(?:fail|error|cancel)/i`, so the helper requires the reason.

**Record 4, the insert now names the conflict arbiter.** Verified against the
shared stack. Without `on_conflict=idempotency_key`, a repeated key answers
`409 {"code":"23505", ... "call_runs_idempotency_key_key"}`. With it, the same
body answers `201 []`, and a body holding one present key and one new key
answers `201` with only the new row. A repeat materialisation therefore creates
no row and records no event. The 409 the module used to raise was not load
bearing as a guard, because the unique constraint is the guard. It was load
bearing as a bug, because it failed the whole insert, so one already-present key
blocked every new row in the same batch. Reverting the arbiter fails
`a second materialisation relies on the durable key and creates no duplicate`
with `call_runs insert failed`, and the live driver then throws
`Uncaught (in promise) Error: call_runs insert failed` on the repeat pass.

**Record 5, thin details and loose ends.** `webhook_received` does not name the
delivered event id. Judged a false positive. The id lives on
`call_runs.terminal_writer` as `webhook:<event_id>` and in `webhook_events`, the
`refetched` row beside it names the outcome, and a redelivery of the same event
appends no second pair, which I measured. The `claimed` detail names the
transition and not the invocation. Judged a false positive. The claim RPC is
atomic, so only the winning tick appends, and the row answers "claimed, at this
instant". The dev
seed writes the kind `completed`, which is not in the vocabulary. Judged a
false positive against T2.9, because `supabase/seed.sql:132-135` is T1.6's file
and no production path can write it, since the helper rejects it for every
caller. The lost `materialised` append is now the M finding above.

## Residual risk

1. A permanently failing append leaves the timeline short with no repair path.
   The record discloses this. A unique index on `(call_run_id, kind)` cannot
   carry the repair, because `polled` and `finalised` repeat.
2. Six of the eight kinds have no enforced detail shape, so a future caller can
   append `{}` for `claimed`, `dispatched`, `polled`, `webhook_received`,
   `refetched` or `ingested`. Only `finalised` and `materialised` are
   constrained today. No observed caller does this.
3. `finalise.ts`'s `appendTimelineRow` retries three times, so an insert that
   commits behind a lost response can write two `finalised` rows. The project
   prefers a duplicate to a loss, so I do not raise it.
4. The dev seed's `call_events` rows carry the kind `completed`. A reader should
   not treat `supabase/seed.sql` as the vocabulary.
5. The dry-run mask keeps the leading seven characters of a number. T2.8 owns
   that helper. My scan of 51 rows found no secret and no unmasked number, and
   the stored dry body keeps the leading seven characters of the callee number
   and masks the rest.
